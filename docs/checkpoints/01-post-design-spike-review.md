# Capper architecture interview review

Based on the current `mvp-technical-design-document.md`, reread from disk on November 17, 2026. Use the cited TDD sections for each question and follow-up. Treat illustrative cases as fixtures and marked defaults as defaults. Work through one question at a time. Capture agreed findings in `second-agent` for later reconciliation.

The planned Docker runtime is included. Pre-Docker setup, tooling trivia, and syntax are outside this review.

## Findings from the walkthrough

- Topic 29 · Presentation follow-up for `future-considerations.md`: Before presenting, review how to debug a slow, expensive, or incorrect LLM turn. Practice reading a turn trace and its model and tool spans, interpreting input, output, and cached token counts, and using time to first token, retries, and compaction events to narrow down the cause.

- Topic 24 · Presentation follow-up for `future-considerations.md`: Highlight the MVP safety-routing feature. A lighter model checks whether the request needs a detailed safety policy while Capper assembles context. If the check times out, the chat request proceeds with the core safety instructions and can still retrieve a detailed policy on demand.

- Topic 22 · Follow-up for `future-considerations.md`: Discuss with the build session whether Capper should flush prepared Harness compaction summaries asynchronously at turn end. A usable summary and its cutoff could be saved to shared storage before a later model call applies it, so another instance can pick it up. Sam will research the Harness integration and persistence timing during that discussion. Outside MVP scope.

- Topic 20 · Follow-up for `future-considerations.md`: Consider estimating the assembled request size before sending it and reducing eligible context if it is near the provider limit. Alternatively, catch a context-limit rejection, rebuild a smaller request, and retry that model call with a bounded retry policy. The reactive approach adds a failed round trip and must preserve valid tool-call/result pairs and avoid replaying completed tool actions or duplicating streamed output. The MVP surfaces the overflow error.

- Topic 17 · Follow-up for `future-considerations.md`: Test whether naming avoided products in the model's account context makes them more likely to surface in generated replies despite the negative instruction. Compare the current approach with enforcing the saved associations in catalog queries and card validation while exposing avoided products only when the user asks to view or change the list. Preserve the ability to identify which product the user wants to remove.

- Topic 16 · MVP feedback for the build session: Consider adding date-range filters and a way to retrieve a bounded batch of transcript messages by position. This would let Capper inspect messages from a specific day or around a point in the transcript without requiring a keyword match. Review for MVP inclusion.

- Topic 15 · Follow-up for `future-considerations.md`: Consider keeping a turn-local set of product IDs returned by catalog queries. Before `show_products` emits cards, check that every requested ID is in that set as well as passing the existing catalog and avoid-list checks. If an ID is outside the set, emit no cards for that call and return a tool error asking the model to look up the product first. This catches hallucinated IDs that happen to refer to real, eligible products the model was never shown during the turn. Outside MVP scope.

- Topic 14 · Follow-up for `future-considerations.md`: Keep the MVP pagination behavior. For future builds, consider persisting the original query and its next cursor as application state so “show me more” can resume the search after many model calls, even if the original tool result has been cleared or compacted.

- Topic 13 · Follow-up for `future-considerations.md`: School-based product popularity is an MVP placeholder to demonstrate how recommendations could use location or demographic groupings. Review the privacy implications of using school affiliation, especially when a school has few users. Sam would require the client's business sign-off before shipping school-based recommendations to production.

- Topic 12 · Follow-up for `future-considerations.md`: Explore semantic catalog search for a future build. Embed product names and descriptions and use query embeddings to find relevant products that literal matching misses, such as a search for “commuter backpack” finding a “compact daypack.” Keep the existing `search_products` interface and enforce the saved avoid list in code. Compare retrieval quality against the MVP’s literal search before choosing an approach.

- Topic 9 · Follow-up for `future-considerations.md`: Explore how admins could add or edit company content and how it could be normalized before publication. Options include uploads to S3 that trigger an LLM-assisted ingestion job, or an admin portal where staff edit individual rules and FAQ entries. An LLM reviewer could flag inconsistencies for human review. Consider a CI/CD-style publishing pipeline that stages changes and runs normalization and validation before activation. Publishing risk to review: always-loaded content is included in the model’s instructions. A malicious edit or upload could put attacker-controlled directions in that channel if it passes review and is published. Consider who can edit, approve, and activate content, and whether uploaded reference material should reach the model as data. These are future design options. The MVP uses hand-curated Markdown.

- Topic 8 · Follow-up for `future-considerations.md`: Keep the ordered `messages.parts` JSON array for the MVP. Queries across conversations by part type or field, such as counting how often a particular product card was included in saved replies, must expand the arrays and inspect each part. Sam wants to revisit this tradeoff and develop an alternative during the future-considerations review.

- Topic 26 · Follow-up for the next session: add a note to `future-considerations.md` that the API assumes the integrating client can generate an `Idempotency-Key` for each logical send and reuse it across retries of that send. Sam wants to think through this integration assumption before presenting.

- Topic 3 · Follow-up for future review: SQLite makes the demo self-contained. For a real client, Sam would recommend moving to the client's managed database or a server database such as PostgreSQL early, especially if Capper will run across multiple instances or handle concurrent writes. Discuss the migration timing before presenting.

- Topics 18, 29, and 30 · Discuss with the build session: add model-call provenance to the normal trace, including the model and content version, summary ID and history cutoff when applicable, tools called, and whether compaction ran. Keep full conversation text out of routine logs. For seeded demo or eval runs, consider opt-in capture of the exact outbound request after Harness and request-only context injection, paired with the model response. Capture per model call because a turn can include multiple calls around tool results. This is for diagnosing what the model saw when an answer fails an eval.

- Topics 22–23 · Discuss with the build session: capture the exact cutoff when Harness applies a summary, and carry that boundary alongside the in-memory summary back to Capper. Prefer an explicit boundary supported by the pinned Harness integration over inferring the cutoff from the resulting history length (CMP-7). If Harness exposes a position or message identity, Capper maps it to `model_messages.id` and saves that ID and the summary together at turn end. Verify what the pinned version exposes before choosing the integration.
